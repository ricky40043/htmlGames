# YouTube 系統設計 Demo：面試問答與展示稿

審查日期：2026-10-05。以下依這個專案的實際能力準備；「正式系統應如何做」不等於本平台已實作。

## 開場 30 秒

「這是我做的 YouTube 類型系統設計教學平台。它在瀏覽器內模擬觀眾、傳輸、佇列、故障和重試，用來讓架構選擇的影響可以被觀察。月份課程用來講解完整流程，即時模式用來追蹤同一位觀眾與 Request。它沒有連接真正的影音後端；選舉、DRM、真實轉碼與雲端帳單不在這個模型內。」

## 建議展示順序（約 6–8 分鐘）

1. 從第 14 章開始，指出上傳與觀看兩條路徑。不要逐一介紹所有按鈕。
2. 切到即時模式，先暫停；關閉隨機故障、隨機移動與持續進出，讓操作可重現。
3. 追蹤觀眾 #1，恢復時間，把觀眾放到弱網區。展示緩衝下降與等待，再移回良好網路。解釋 CDN 不能消除最後一哩瓶頸。
4. 展示 API 容量實驗：少量工作槽、送出一批請求，觀察排隊與逾時，再增加容量，追蹤同一批請求完成。
5. 展示上傳生命週期：建立 Metadata → 分塊確認 → 檢查 → 多畫質／縮圖 → 發布。若展示 96 MB，需預留傳輸時間；20x 是目標倍率，實際速度看介面。
6. 示範 DB 故障時發布不能成功，恢復 DB 後重試；說明已完成上傳後，創作者離線不應停止後端處理。
7. 最後才切回月份課程，說明兩種模式的用途與限制，避免把教學評分說成真實 SLA。

展示前使用頁面「重新模擬」清除自己的示範進度。不要直接以隨機事故正在發生、或先前故障未恢復的狀態開場。

## 優先準備的問題

### 1. 你實作了什麼？哪些只是圖？

回答：固定 0.1 秒時鐘、觀眾身份、請求狀態、機器工作槽、排隊、逾時、退避重試、播放緩衝、分塊確認及轉碼相依任務是可執行的模型。完整課程動畫另外有自己的流程與資料表；它與即時世界不是逐筆一致的執行紀錄。沒有真正影音編碼、持久化 DB、CDN 或網路封包。

追問準備：指出 `youtube-world.js` 的模型、`youtube-world-ui.js` 的呈現層，以及新增回歸測試，展示你能用故障案例驗證規則。

### 2. 為什麼影片與 Metadata 分開？

回答：影片是大型物件，適合物件儲存；Metadata 是小型、可查詢的結構化資料。兩者有不同讀寫特性。先建立穩定的 video ID，讓上傳 session、轉碼工作與發布狀態串在一起；不能因為影片位元組傳完就直接宣告 ready。

### 3. 一支影片什麼時候才算發布成功？

回答：原檔完整確認、必要轉碼輸出就緒，以及 Metadata 的 ready 狀態寫入成功之後。本模型等待所有設定的畫質與縮圖完成；正式產品也可以先發布最低可用畫質，再逐步補高畫質，但要定義播放清單與狀態更新規則。

追問：DB 故障時？維持 processing，重試 Metadata 寫入，不能用快取存活來假裝持久化成功。

### 4. 預簽名 URL 為什麼有用？安全嗎？

回答：應用 API 先驗證上傳權限，再給限定物件、操作與有效期限的 URL，大檔案可直傳物件儲存，減少 API 中轉。URL 本身是 bearer token，拿到它的人通常就能在有效範圍內使用；不是每次 PUT 都重新核對登入身份。本平台只模擬直傳路由，沒有簽章與身份驗證。[AWS 官方說明](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

### 5. 上傳中斷為什麼不用全部重來？

回答：保存 upload ID、part number 與已確認的分塊，只重傳未確認部分；全部完成後才組合原檔。完整物件的完成操作、校驗與清理未完成 upload 也需設計。此平台採教學 multipart 模型，並非 YouTube Data API 真實上傳協定的複製。[S3 multipart](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)、[YouTube resumable upload](https://developers.google.com/youtube/v3/guides/using_resumable_upload_protocol)

### 6. 上傳分塊、GOP、播放片段有什麼不同？

回答：上傳分塊是傳輸與重試單位；GOP 是影片編碼的畫面參照群組；播放片段是串流取得的媒體單位。三者不必一對一。分塊能重試不代表能獨立解碼；open GOP 可能跨群組參照。本平台不執行真實編碼或 GOP 切割。[Apple HLS 規格](https://developer.apple.com/documentation/http-live-streaming/hls-authoring-specification-for-apple-devices/)

### 7. 為什麼用 DAG 轉碼？Worker 死掉怎麼辦？

回答：檢查完成後，不同畫質與縮圖可平行做，發布等待必要節點完成。失敗只重跑受影響任務；已完成的其他畫質保留。模型有「重做任務」與「保留工作進度」兩種策略。真正 Checkpoint 需要可恢復的編碼邊界、外部儲存與一致的任務狀態，不是任意一個百分比就能接著轉。

### 8. 上傳者關掉瀏覽器後還能轉碼嗎？

回答：只要原檔已完整提交，後端工作就應獨立執行。這次修正後，模型中的轉碼與發布不再依賴上傳者網路。實際使用者關閉這個教學網頁時，整個 JavaScript 模擬仍會停止；這與模擬中的創作者離線是不同層次。

### 9. 完成事件重複送達，會發布兩次嗎？

回答：正式系統通常要以至少一次投遞為假設，消費端用 event ID、video ID／版本及唯一鍵做冪等處理，DB commit 後再 ack；處理跨儲存一致性可考慮 outbox 與補償。完整圖有完成事件節點，但即時世界沒有真正 durable queue、ack 或 dead-letter queue，不能宣稱已驗證 exactly-once。

### 10. CDN 解決什麼？不能解決什麼？

回答：把可快取內容放近觀眾，減少回源流量與遠端傳輸延遲。Cache miss 仍要回源；CDN 故障可在可用路由上回源。使用者自己的連線太慢時，CDN 也無法讓最後一哩超過其上限。這個模型的 CDN 沒有 TTL、容量淘汰與完整一致性策略。

### 11. 有 CDN 為什麼仍然轉圈？ABR 怎麼決定？

回答：播放器消耗緩衝的速度大於下載速度時會停播。ABR 依近期吞吐、緩衝與安全餘裕決定後續片段畫質；不能把已下載片段瞬間換成另一個編碼。模型提供 360p／480p／720p，適合展示趨勢，不是完整播放器演算法。

### 12. DB 掛掉是不是整站都不能用？

回答：應按操作區分。建立／發布影片需要可靠 Metadata 寫入；已快取的讀取與已取得路徑的影音傳輸，可能繼續提供。模型已修正 Metadata 寫入不能繞過 DB。正式系統還需分析搜尋索引、權限查核、推薦與觀看事件等不同依賴。

### 13. 三個節點能壞兩個嗎？

回答：取決於協定。三節點多數決需要兩個同意，只能容忍一個故障。任一存活快取節點可回應讀取，並不等於三節點 Quorum 的讀寫一致性。本平台是前者的可用性示意，並未實作 Quorum。[etcd failure modes](https://etcd.io/docs/v3.5/op-guide/failures/)

### 14. 多副本、備援與自動擴容差在哪？

回答：本平台固定三台會同時分流，屬於多副本承載；不是兩台閒置等接手。自動擴容則等待同區持續滿載 180 秒再加一台，沒有縮容。真正的策略還要考慮啟動時間、健康檢查、冷卻時間、最低副本數及故障域。

### 15. 為什麼增加 API 機器後仍卡？

回答：瓶頸可能轉到 DB、物件儲存、worker 或使用者網路。先看同類機器的佇列、使用中的工作槽，再追蹤請求路徑。只增加非瓶頸資源，不會讓整條路徑無限加速。用容量實驗展示「同一批請求」的變化。

### 16. 重試會不會雪崩？

回答：模型有有限次數的指數退避，但沒有完整 jitter、全域 retry budget、熔斷、限流與 admission control。正式系統應處理多客戶端同步重試，區分可重試與不可重試錯誤，寫入操作要冪等。

### 17. 你的可用率、QoE 和容量數字可信嗎？

回答：月份評分是預設策略規則，並非實測 SLA。即時模式的排隊與再緩衝是此模型產生的數值；機器容量、網速及修復時間都是示例。真正評估要定義 SLI、觀測窗口、分母、p95／p99、錯誤率和實測容量。失敗「嘗試」也不是失敗「使用者」或最終失敗請求數。

### 18. 你怎麼驗證模擬不是動畫亂跑？

回答：固定種子與時間步長，使相同操作序列可重現；用 Node 測試驗證不變量與失敗恢復，再用瀏覽器確認按鈕真的作用於模型。這次新增 DB 故障不能發布、創作者離線仍發布、失效 CDN 不會被憑空暖快取等案例。確定性不等於與真實基礎設施的效能相同。

### 19. 兩個模式切換會保存什麼？

回答：以 sessionStorage 序列化交接共用觀眾、機器、請求、月份與時鐘；不是後端持久化或多人同步。課程動畫仍保有另一層流程資料，ID 不可逐筆對照。真實跨裝置協作需要後端狀態儲存、版本及衝突處理。

### 20. 如果變成正式產品，優先補什麼？

回答：先定義需求與 SLO，再接上真正身份驗證、物件儲存上傳與持久化 Metadata；加入可靠工作佇列與冪等 consumer；執行實際轉碼與播放清單生成；最後用觀測資料、壓測與故障演練驗證容量。平台本身則優先統一兩種模式的執行模型，讓所有視圖引用同一組請求與生命週期。

## 不要說成已完成的功能

- 「這就是 YouTube 真正的內部架構。」應說教材啟發的示意設計。
- 「三節點 Quorum 壞兩台仍能正常讀寫。」
- 「預簽名 URL 只有原登入者可以使用。」
- 「所有 GOP 都能獨立播放，所以才能重試。」
- 「已做 DB 選舉、跨節點資料複寫、Exactly-once 或真正 Checkpoint。」
- 「月度 99 分就是 99% SLA」「500 人操作上限就是伺服器極限」。
- 「兩個畫面的每個 Request ID 與完成時間都一樣」。
