## 序章　課程導覽


### 這堂課要解決什麼問題？（0:00）

嗨，歡迎來到這堂課。今天我們要一起設計一個飯店訂房系統。內容以《System Design Interview 第二卷》第七章為主，再搭配投影片，從問需求一路做到扛得住高併發的架構。

想像你是萬豪 Marriott 這種連鎖飯店的工程師，老闆要你做官網的訂房系統。好消息是，這題學會了，Airbnb、訂機票、訂電影票，其實都是同一個套路。

整堂課照系統設計面試的四個步驟走：先把問題和範圍問清楚，再畫出高階設計，接著挑重點深入，最後收尾總結。

其中第三步是重頭戲，會深入四件事：資料模型怎麼改、並行時怎麼不出錯、流量大了怎麼擴、微服務之間資料怎麼保持一致。每一章都有可以自己動手玩的實驗，看到黃色標籤，就換你上場。

先送你一句話，整堂課都會用到：這個系統真正難的不是流量，而是同一間房，絕對不能賣兩次。好，我們從需求開始。


**重點筆記**

- 教材主軸：《System Design Interview Vol.2》第 7 章「飯店預訂系統」（p.233–266）＋《飯店預訂系統設計藍圖》投影片。
- 同樣的設計可套用到：Airbnb、航班訂位、電影票訂位。
- 全課核心一句話：**同一間房，不能賣兩次。**


## 第 1 章　第 1 步：釐清需求與粗略估算


### 面試對話：先問清楚範圍（1:24）

面試一開場，千萬別急著畫架構圖。訂房系統的長相，會隨業務情境差很多，所以第一件事是問問題、把範圍縮小。我們來重播一段對話。第一題：系統規模多大？

第二題：客人是訂房時付錢，還是到飯店才付？面試官說，簡單起見，訂房時就付全額。這一句話，代表訂單一定會有「付款中、已付款」這類狀態。

第三題：只有網站和 App 嗎？要不要支援電話訂房？答案是只有網站和 App。第四題：可以取消嗎？可以。

接著問：還有什麼要注意的嗎？面試官丟出一個關鍵需求：允許 10% 的超額預訂，英文叫 overbooking。

超額預訂聽起來很怪，為什麼要故意多賣？因為飯店很清楚，一定有人會臨時取消或沒出現。所以一百間的房型，系統最多可以賣到一百一十間。航空公司超賣機位，也是同樣的道理。

這時候應試者主動收斂範圍：搜尋功能技術上沒什麼挑戰，這次先不做。我們專心做五件事：飯店頁、房間詳細頁、訂房、管理後台的新增修改刪除，還有超額預訂。

最後面試官補了一句：房價每天都不一樣，是看當天預計有多少人入住來決定的。這句話要記住，它會直接影響我們怎麼設計資料表。


**重點筆記**

- 規模：5,000 家飯店、1,000,000 間客房
- 付款：預訂時付全額
- 通路：只有網站 / App（不含電話訂房）
- 可取消預訂
- **10% 超額預訂（overbooking）**：100 間最多賣 110 間
- 不做搜尋功能；重點功能：飯店頁、房間詳細頁、預訂、管理後台、超額預訂
- **動態定價**：房價由當天預計入住人數決定，每天可能不同


### 非功能性需求（3:19）

功能講完，再來是非功能需求。第一個是高並行。想像跨年煙火那晚，熱門飯店只剩幾間房，可能同一時間有一堆人在搶同一間。

第二個是延遲。客人當然希望越快越好，但按下訂房之後，轉個兩、三秒才完成，其實大家都能接受。

把這兩點放在一起，方向就很清楚了：我們可以拿一點點速度，去換正確性。寧可慢一點，也不能把同一間房賣給兩個人。


**重點筆記**

- **高並行（concurrency）**：旺季、大型活動時，熱門飯店會有很多人同時搶訂同一間客房。
- **中等程度的延遲**：回應越快越好，但預訂請求花幾秒處理也可接受。
- 推論：可以用一點延遲換取正確性（鎖、交易）。


### 粗略估算（Back-of-the-envelope）（4:00）

接下來做個粗估，也就是面試官最愛的「信封背面計算」。已知五千家飯店、一百萬間客房。我們假設七成的房間會被訂走，平均住三天。

一天會有多少筆訂單？一百萬乘以零點七，再除以三，大約二十三萬三千筆。為了好算，抓整數二十四萬。

一天有八萬六千四百秒，粗抓成十的五次方。二十四萬除以十萬，每秒的訂房交易量，也就是 TPS，大概只有 3。

每秒才 3 筆，是不是比你想像的小很多？這告訴我們，寫入量根本不是問題。真正的挑戰有兩個：一是正確性，二是大量的讀取流量。

🧪 【互動實驗】換你玩玩看。拖拉滑桿，改改客房數、住房率和入住天數，看 TPS 和各頁面的 QPS 怎麼變。也可以把倍數拉到一千倍，感受一下 Booking.com 那種等級的流量。


**重點筆記**

- 每日預訂量 = 1,000,000 × 0.7 ÷ 3 = 233,333 ≈ **240,000**
- 1 天 ≈ 86,400 秒 ≈ 10^5 秒
- 預訂 TPS = 240,000 ÷ 10^5 ≈ **3**
- TPS 極低 ⇒ 瓶頸不在寫入吞吐量，而在**正確性**與**讀取流量**。


### QPS 漏斗：讀多寫少（5:14）

再來估每個頁面的 QPS。一般人訂房會走三步：先逛飯店和房間的詳細頁；再進到確認頁，看日期、人數、付款資訊；最後才按下訂房。前兩步都是查詢，只有最後一步是真正的交易。

我們假設每往下一步，只有一成的人會繼續，剩下九成看一看就走了。另外也假設系統不會預先載入下一頁的資料。

已知最後一步是每秒 3 筆，往回推：確認頁就是 3 除以一成，等於 30；詳細頁再除一次，等於 300。

結論很清楚：這是一個非常典型、讀多寫少的系統，讀寫大概一百比一。這個比例，會一路影響我們選資料庫、加快取，還有整個架構怎麼長。


**重點筆記**

- 使用流程：① 看飯店／房間詳細頁（查詢）→ ② 看訂單確認頁（查詢：日期、人數、付款資訊）→ ③ 按「預訂」（transaction 完整交易）
- 假設每一步只有 10% 繼續、90% 離開，且不做 prefetching
- 反推：TPS 3 → 確認頁 QPS 30 → 詳細頁 QPS 300
- 結論：**極端讀多寫少**，讀寫比約 100:1


## 第 2 章　第 2 步：API 設計


### RESTful API 總覽（6:17）

第二步，開始畫高階設計，包含三塊：API、資料模型、整體架構。先從 API 開始，用大家熟悉的 RESTful 風格。搜尋 API 雖然重要，但沒什麼技術難度，這裡先跳過。

飯店相關的 API：用 GET 拿飯店資訊；新增、修改、刪除飯店，分別是 POST、PUT、DELETE。注意，這三支會改資料的，只有飯店員工能呼叫。

房間的 API 長得一模一樣，只是路徑掛在飯店底下，例如 hotels 斜線 ID 斜線 rooms 斜線 ID。同樣地，改資料的只開放給員工。

真正的主角是預訂 API。GET reservations 拿到我自己的訂單清單；後面加 ID 看單筆細節；POST 下一筆新訂單；DELETE 取消訂單。


**重點筆記**

- 第 2 步三個主題：API 設計、資料模型、高階設計
- 搜尋 API 重要但無技術挑戰，本章略過
- 飯店／房間的 POST、PUT、DELETE 僅供**飯店工作人員**使用
- 預訂 API：`GET /v1/reservations`（已登入使用者的紀錄）、`GET /v1/reservations/ID`、`POST /v1/reservations`、`DELETE /v1/reservations/ID`（取消）


### POST /v1/reservations 與冪等鍵（7:18）

我們來看最關鍵的這支：下訂單。請求裡帶了入住日、退房日、哪間飯店、哪間房，還有一個 reservationID。

請特別注意這個 reservationID。它的身分是冪等鍵，用途是防止重複訂房，也就是同一天、同一間房，被同一個人訂了好幾次。

冪等是什麼意思？就像電梯的按鈕，你按一下跟狂按十下，電梯都只會來一次。同一個請求不管送幾次，結果都一樣。先記住它，第六章會把它拆開來講。

再埋一個伏筆：這裡用的是 roomID，也就是指定某一間實體房間。對 Airbnb 很合理，但對連鎖飯店其實是錯的。為什麼？第五章揭曉。

🧪 【互動實驗】換你試試看。點左邊每一支 API，看看請求和回應長什麼樣子。切換旅客和員工身分，看哪些會被擋下來。也試試看連按兩次下訂單，第二次會發生什麼事。


**重點筆記**

```
{
  "startDate": "2021-04-28",
  "endDate": "2021-04-30",
  "hotelID": "245",
  "roomID": "U12354673389",
  "reservationID": "13422445"
}
```

- `reservationID` 作為**冪等鍵（idempotency key）**，防止重複預訂（同一天對同一間房進行多次預訂）。
- 冪等：同一個請求呼叫多少次，結果都一樣。
- 伏筆：`roomID` 綁定實體房間，第 5 章會改成 `roomTypeID`。


## 第 3 章　第 2 步：資料模型與選型


### 先看查詢模式，再選資料庫（8:34）

選資料庫之前，有個好習慣：先想清楚資料會怎麼被查。這個系統主要有四種查詢。

第一，查飯店的詳細資訊。第二，給一段日期，找出還有哪些房型可以訂。第三，把一筆訂單記下來。第四，查某筆訂單，或是過去的訂房紀錄。

從估算我們知道，系統規模不算大，但要撐得住大型活動時的流量高峰。綜合來看，我們選關聯式資料庫，理由有三個。


**重點筆記**

- 查詢 1：查看飯店相關的詳細資訊
- 查詢 2：在給定日期範圍內，找出可預訂的房型
- 查詢 3：把預訂結果記錄起來
- 查詢 4：找出某個預訂紀錄，或是過去的預訂歷史
- 系統規模不大，但要為大型活動的流量高峰做準備 → 選擇關聯式資料庫


### RDBMS vs NoSQL（9:14）

第一，讀多寫少。逛網站的人，永遠比真正下訂的人多很多。NoSQL 很多是為了大量寫入而最佳化，在這裡強項派不上用場。

第二，也是最重要的：ACID，原子性、一致性、隔離性、持久性。訂房牽涉到錢和庫存，沒有 ACID，你就很難保證不會出現負的餘額、重複扣款、或一房兩賣。有了它，程式碼會簡單很多，系統也比較好理解。

第三，好建模。飯店、房間、房型之間的關係非常清楚，而且不太會變，用表格和外鍵來表達再自然不過。

所以結論是：只要系統碰到金流和庫存，關聯式資料庫的 ACID，就是最穩的選擇。


**重點筆記**

- **讀多寫少**：網站／App 瀏覽人數遠多於實際預訂人數；NoSQL 多針對寫入最佳化，優勢用不上。
- **ACID**（原子性、一致性、隔離性、持久性）：避免負餘額、重複扣款、重複預訂；讓程式更簡單、系統更好理解。
- **容易建模**：hotel、room、room_type 關係清楚穩定。**結論：預訂系統涉及金流與庫存，RDBMS 的 ACID 是最合理選擇。**


### 初版資料表設計（圖 7.2）（10:14）

這是大部分人第一直覺會畫出來的資料表，依照所屬的服務分組。飯店服務底下有兩張表：hotel 放飯店名稱和地址；room 放房型、樓層、房號，還有這間房現在能不能用。

房價服務有一張 room_type_rate，用飯店加日期當主鍵，每天一筆價格，剛好對上每天價格不同的需求。客戶服務則有一張 guest 表。

預訂服務有 reservation 表：訂單編號是主鍵，另外記了飯店、房間、入住和退房日期、狀態，還有是哪位客人。

注意到了嗎？reservation 裡存的是 room_id，代表一筆訂單直接綁定了一間實體房間。先把這個細節放在心上，等一下它就是問題所在。


**重點筆記**

- 飯店服務：`hotel`(hotel_id PK, name, address, location)、`room`(room_id PK, room_type_id, floor, number, hotel_id, name, is_available)
- 房價服務：`room_type_rate`(hotel_id PK, date PK, rate) → 對應「每天不同價」
- 客戶服務：`guest`(guest_id PK, first_name, last_name, email)
- 預訂服務：`reservation`(reservation_id PK, hotel_id, room_id, start_date, end_date, status, guest_id)


### 訂單狀態機（State Machine）（11:14）

大部分欄位一看就懂，只有 status 值得多講。訂單有五種狀態：待處理、已付款、已退款、已取消、已拒絕。

訂單剛建立時是待處理，等客人付款。客人自己取消，就變成已取消；付款失敗或被系統擋下，就變成已拒絕。

付款成功變成已付款。付完之後如果要退訂，走完退款流程，就變成已退款。

工程上的重點是：狀態只能沿著箭頭走。已取消不能突然變成已付款，已退款也不能再退一次。寫程式的時候，在更新語句裡加上「目前狀態必須是什麼」，如果影響筆數是零，就代表有人搶先改掉了。

🧪 【互動實驗】換你試試。對同一筆訂單觸發各種事件，看哪些會成功、哪些會被拒絕。也可以按「同時付款加取消」，看看條件式更新怎麼保護你。


**重點筆記**

- status：`pending` 待處理、`paid` 已支付、`refunded` 已退款、`canceled` 已取消、`rejected` 已拒絕
- pending →(使用者取消) canceled；pending →(支付成功) paid；pending →(支付失敗／系統阻擋) rejected；paid →(退訂與退款) refunded
- 實作建議：`UPDATE … SET status='paid' WHERE reservation_id=? AND status='pending'`，影響列數為 0 代表狀態已被他人改變（條件式更新，防併發非法轉移）


### 問題：訂的是「房間」還是「房型」？（12:27）

這份初版設計有個不小的問題。如果是 Airbnb，完全沒毛病：你訂的就是那一間特定的房子，下訂當下就知道是哪一間。

但飯店不是這樣。你在萬豪訂房時，選的是「King 大床房」這種房型，而不是 1201 號房。真正的房號，要等你到櫃台辦入住時才會拿到。

看動畫：三位客人都訂了 King 房型，系統只是把 King 房型的已訂數量加一。等到入住那天，櫃台才把 1201、1305、1418 分給他們。

所以這裡有個架構原則：資料模型要反映「訂的是房型」這個現實，而不是直接綁死某一間房。怎麼改？第五章見。


**重點筆記**

- **Airbnb 模式**：預訂某個特定實體房源，下訂當下即綁定 room_id／listing_id（user_123 → Room 101）
- **Marriott 模式**：預訂某一種**房型**（標準房、King size 特大床、兩張 Queen size 床…），只鎖定房型庫存；房號在入住時才由櫃台分配（user_123 → King Size Type）
- 架構準則：資料模型必須反映「房型預訂」的現實


## 第 4 章　第 2 步：高階架構設計


### 微服務架構全貌（圖 7.4）（13:24）

架構我們採用微服務，Amazon、Netflix、Uber、Airbnb 都是這樣做。我們從上往下，一個一個元件來看。最上面是使用者，用手機或電腦來訂房。

第一站是 CDN。圖片、JavaScript、HTML 這些不會變的靜態檔案，全部放在 CDN 上，使用者就近拿，主系統的負擔一下子就輕很多。

第二站是 API 閘道器，你可以把它想成大樓的警衛加總機：負責限流、驗證身分，再把請求轉到正確的服務。例如看飯店頁就轉給飯店服務，要訂房就轉給預訂服務。

閘道器後面有四個核心服務。第一個是飯店服務，提供飯店和房間的資料。這些資料幾乎不會變，非常適合加快取，那每秒三百次的瀏覽流量，大部分都在這裡被吃掉。

第二個是房價服務，提供未來每一天的房價。旅館業有個有趣的地方：房價是看當天預計會住多少人來決定的。

第三個是預訂服務，負責接單、預訂房間，並且在訂房或取消時追蹤庫存。它是整個系統的心臟。

第四個是支付服務，負責收錢。付款成功就把訂單改成已付款，失敗就改成已拒絕。

右邊是員工的世界。飯店員工透過 VPN 連進內部 API，使用飯店管理服務：看今天有誰要入住、幫客人訂房、取消、退款、更新房間資訊等等。


**重點筆記**

- **使用者**：透過手機或電腦預訂
- **管理者**：已授權飯店員工；退款、取消預訂、更新房間資訊
- **CDN**：快取所有靜態資源（JavaScript、圖片、影片、HTML）

### 從 roomID 到 roomTypeID（16:15）

### room_type_inventory 逐欄解析（16:53）

我們一個欄位一個欄位看。hotel_id 是哪家飯店，room_type_id 是哪種房型，date 是哪一天。

total_inventory 是這種房型總共有幾間，但要扣掉暫時不能賣的。比如有兩間在整修，那就從一百零二間變成一百間。

total_reserved 是這家飯店、這種房型、這一天，已經被訂掉幾間。可以賣的數量，就是總數減掉已訂。

設計的關鍵是：每一天一筆資料。這樣要查一段日期、或處理一段日期的訂單都很直覺。飯店、房型、日期三個欄位合起來當主鍵。

那資料從哪來？我們會先把未來兩年每一天的資料都建好，再排一個每天跑的排程，每過一天，就往後補一天。


**重點筆記**

- `hotel_id`：飯店 ID；`room_type_id`：房型 ID；`date`：單一日期
- `total_inventory`：房間總數，**扣掉暫時下架**（例如維護）的數量
- `total_reserved`：該 hotel_id + room_type_id + date 已被預訂的總數
- **每個日期一行** → 管理日期範圍內的預訂、查詢都很容易
- 複合主鍵 `(hotel_id, room_type_id, date)`
- 預先填入未來 2 年的庫存；每日排程每過一天補一天


### 儲存量估算與高可用（17:54）

算一下會有多少資料：五千家飯店，假設每家二十種房型，乘以兩年，再乘以三百六十五天，總共七千三百萬筆。

七千三百萬筆其實不多，一台資料庫就放得下。問題是只有一台的話，它一掛，整個系統就停擺。所以我們在不同的地區或可用區放幾份副本，主庫壞了，副本馬上頂上來。

這是庫存表的樣本資料。例如飯店 211 的房型 1001，在 2021 年 6 月 1 號總共一百間、已訂八十間；同一個房型的資料一路建到兩年後，那天的已訂當然還是零。


**重點筆記**

- 5,000 家飯店 × 20 種房型 × 2 年 × 365 天 = **7,300 萬行**
- 單一資料庫就足以保存，但有**單點故障**風險
- 高可用：跨多個 region 或 availability zone 設定資料庫副本


### 查詢「能不能訂」＋超額預訂（18:45）

有了這張表，怎麼判斷能不能訂？輸入是：入住日、退房日、房型、飯店，還有要訂幾間。輸出很單純：可以就回傳 true，不行就是 false。

用 SQL 來做分兩步。第一步，把這段日期的每一天都撈出來。結果是：七月一號已訂 97、二號 96、三號 95，總數都是 100。

第二步，程式一天一天檢查：已訂數量加上這次要訂的，有沒有超過總數。每一天都沒超過，才代表整段日期都有房。

還記得超額預訂嗎？在這個設計下超簡單，只要把右邊的總數乘上百分之一百一十就好。

舉個例子，一次要訂四間呢？七月一號是 97 加 4 等於 101，超過 100，正常情況不行。但開了 110% 的超賣，上限變成 110，101 就沒問題。

🧪 【互動實驗】換你試試。選日期範圍、房間數，開關超額預訂，看系統怎麼一天一天檢查。你也可以直接改每天的已訂數量，製造一些邊界情況。


**重點筆記**

- 輸入：startDate、endDate、roomTypeId、hotelId、numberOfRoomsToReserve；輸出：true / false
- 步驟 1：`SELECT date, total_inventory, total_reserved FROM room_type_inventory WHERE room_type_id=? AND hotel_id=? AND date BETWEEN ? AND ?`
- 步驟 2：逐行檢查 `total_reserved + n <= total_inventory`，全部 true 才可訂
- 10% 超額預訂：`total_reserved + n <= 110% * total_inventory`


### 資料量太大怎麼辦？（20:10）

面試官常會追問：訂單越來越多，一台資料庫放不下怎麼辦？第一招，只留現在和未來的資料。過去的訂房紀錄很少有人查，可以封存起來，甚至搬去便宜的冷儲存。

第二招，分片。最常見的兩種查詢，下訂單和查我的訂單，都會先指定飯店，所以拿 hotel_id 來切非常合適：把 hotel_id 雜湊之後，對伺服器數量取餘數。實際示範放在第七章。


**重點筆記**

- 策略 1：只保存目前與未來的預訂資料；歷史紀錄不常被存取，可封存，甚至轉移到**冷儲存**
- 策略 2：**資料庫分片**。最常見查詢：進行預訂、按使用者名字查預訂紀錄，兩者都先選定飯店 → `hotel_id` 是好的分片鍵：`hash(hotel_id) % number_of_servers`


## 第 6 章　第 3 步・深入②：並行問題


### 兩種「重複預訂」（20:48）

接下來是整堂課最核心的問題：重複預訂。它其實有兩種：第一種，同一個人手滑連點了好幾次；第二種，很多人在同一瞬間，搶同一間房。


**重點筆記**

- 同一個使用者點擊很多次「預訂」按鈕
- 多個使用者嘗試同時預訂同一個房間（房型）


### 情境 1：同一個使用者點了兩次（21:04）

先看第一種。使用者點了兩次訂房按鈕，送出兩個一模一樣的 INSERT。

如果什麼都沒擋，資料庫就多了兩筆一模一樣的訂單。同一個人、同一天、同一種房，可能還被扣了兩次錢，客服電話馬上就來了。

最直覺的解法是在前端擋：按下去之後，把按鈕變灰、停用。大部分情況有用，但並不可靠。使用者可能關掉了 JavaScript；網路一不穩，瀏覽器或 App 自己重送；甚至有人直接用程式打你的 API，根本不會經過你的按鈕。

所以真正的防線，一定要放在伺服器端：在 API 加上冪等鍵。同一個請求打一百次，結果都跟打一次一樣。


**重點筆記**

- 圖 7.7：兩次 INSERT → 資料表出現兩筆相同訂單
- **客戶端解法**：送出後把「提交」按鈕反灰／停用／隱藏。不可靠：使用者可能停用 JavaScript 繞過檢查，或因網路問題意外送出兩次
- **API 解法**：在預訂 API 請求中加入**冪等鍵**；API 無論被呼叫多少次都產生相同結果 = 冪等（idempotent）


### 冪等鍵的完整流程（圖 7.8～7.10）（22:04）

我們走一遍完整流程。第一步，客人選好房型、入住和退房日期，按下「繼續」，預訂服務就先生成一張訂單草稿。

第二步，系統顯示確認頁讓客人檢查。就在這時候，ID 產生器給這張訂單一個全世界唯一的 reservation_id，跟著回應一起送回前端。

第三步 a，客人按下「完成預訂」，請求裡帶著這個 ID。它剛好就是訂單表的主鍵，第一次寫入，成功。

第三步 b，客人又手滑按了一次。第二個請求帶著同一個 ID 進來，因為主鍵不能重複，資料庫直接拒絕。重複訂單，就這樣被擋下來了。

為什麼有效？看這兩個 INSERT，第一個值都是 121。第一個寫進去了；第二個撞到主鍵的唯一限制，被資料庫擋掉。表裡永遠只會有一筆。

補充兩件事。第一，冪等鍵不一定要用 reservation_id，書上選它只是因為它現成又剛好合用。第二，實務上撞到主鍵時，別回錯誤，直接回傳第一次的結果。這樣前端就算重試，也會拿到成功，這才是使用者感受得到的冪等。

🧪 【互動實驗】換你試試。在模擬器裡狂點完成預訂，或是模擬網路逾時自動重試。開關冪等鍵和按鈕停用，看最後資料表裡有幾筆訂單、被扣了幾次錢。


**重點筆記**

- 生成預訂訂單：顧客輸入房型、入住／退房日期，點「繼續」→ 預訂服務生成訂單
- 系統顯示確認頁；**ID 生成器**產生全域唯一的 `reservation_id`，作為 API 回應送回客戶端
- 3a. 第一次提交，請求包含 reservation_id（預訂表主鍵）
- 3b. 再次點擊「完成我的預訂」→ 第二次提交；因 reservation_id 是主鍵，唯一性限制擋下重複預訂
- 不一定要用 reservation_id 當冪等鍵；選它是因為它是現成欄位且適合
- 實務補充：把「主鍵衝突」轉為回傳第一次的結果，客戶端重試也拿到成功


### 情境 2：最後一間房的競爭狀況（圖 7.11）（23:56）

第二種情況比較棘手：很多人同時訂同一種房型，可是只剩一間。目前總共一百間，已經訂了九十九間。我們把使用者一的交易叫 T1，使用者二的叫 T2。

先講個前提：資料庫的隔離等級不是最嚴格的序列化。隔離等級由寬到嚴，有讀未提交、讀已提交、可重複讀，還有序列化。只有序列化，才保證大家同時做事的結果，跟排隊一個一個做一樣。

時間開始走。T2 先檢查：99 加 1 沒超過 100，還有一間，沒問題。

T1 也來檢查：它看到的也是 99，同樣覺得還有一間。

T1 先動手，把已訂數量更新成 100。

接著 T2 也訂房。因為隔離性，T1 還沒提交的修改，T2 是看不到的。所以 T2 看到的還是 99，也算出 100 寫回去。

T1 提交，T2 也提交。結果呢？明明只剩一間房，兩個人都訂到了。資料庫寫著 100，實際上卻賣了 101 間。這就是經典的「先檢查、再寫入」的競爭問題。

給工程師補充一下：書上的例子是程式先算好 100 再寫回，所以後寫的蓋掉先寫的。如果改成 total_reserved 等於 total_reserved 加一，InnoDB 會讓 T2 等 T1 提交完再算，得到 101。更新不會遺失了，但一樣超賣，因為檢查和寫入之間根本沒被保護。


**重點筆記**

- 假設**不是** serializable 隔離等級；總庫存 100、已訂 99（只剩 1 間）
- 隔離等級由低到高：Read Uncommitted → Read Committed → Repeatable Read → Serializable
- 交易 2、交易 1 都檢查 `total_reserved + rooms_to_book <= total_inventory` → 都是 true
- 交易 1 更新為 100；交易 2 因**隔離性**看不到交易 1 未提交的變動，看到的仍是 99，也更新為 100
- 兩者都提交 → 只剩 1 間，系統卻接受兩人預訂
- 補充：若寫成 `SET total_reserved = total_reserved + 1`，InnoDB 會讓後者等待並得到 101，避免 lost update，但仍然超賣（因為檢查已經通過）


### 預訂的 SQL 偽代碼與三種解法（25:52）

在修之前，先看訂房的 SQL 長怎樣。它分兩段：先檢查庫存，再把房間訂下來。

問題就出在這兩段中間的縫：你檢查完、還沒寫進去的那一瞬間，別人可以插隊。要補這個縫，就需要某種鎖。我們來看三種做法：悲觀鎖、樂觀鎖，還有資料庫約束。


**重點筆記**

```
# 步驟 1：檢查房間的庫存狀況
SELECT date, total_inventory, total_reserved
FROM room_type_inventory
WHERE room_type_id = ${roomTypeId} AND hotel_id = ${hotelId}
AND date between ${startDate} and ${endDate}

# 針對步驟 1 送回來的每個項目
if ((total_reserved + ${numberOfRoomsToReserve}) > 110% * total_inventory) {
  Rollback
}

# 步驟 2：預訂房間
UPDATE room_type_inventory
SET total_reserved = total_reserved + ${numberOfRoomsToReserve}
WHERE room_type_id = ${roomTypeId}
AND date between ${startDate} and ${endDate}

Commit
```
三種技術：悲觀鎖定、樂觀鎖定、資料庫約束


### 選項 1：悲觀鎖定（SELECT … FOR UPDATE）（26:21）

第一種，悲觀鎖。它的心態是「一定會有人跟我搶」，所以一開始就先把資料鎖起來。其他人想改，就得排隊等我改完、提交、解鎖。

在 MySQL 裡，就是在 SELECT 後面加 FOR UPDATE，查到的每一筆都會被鎖住。T1 先執行，T2 執行同一句時就被卡住，只能等。

T1 檢查完還有房，更新、提交，已訂變成 100，鎖也放開了。

這時候 T2 才拿到鎖，讀到的是 100，發現已經沒房，於是撤銷交易。結果完全正確，只賣出一間。

悲觀鎖的優點：不會改到別人正在改的資料；實作簡單，大家排隊就不會衝突。如果搶的人非常多，它其實很好用。

但缺點很致命。第一，鎖的東西一多，就可能死鎖：T1 拿著七月一號等七月二號，T2 拿著七月二號等七月一號，兩個人互相卡死。第二，擴展性差：一個交易鎖太久，後面全部塞車。所以書上不推薦訂房系統用悲觀鎖。


**重點筆記**

- 又稱悲觀並行控制：使用者一開始更新某筆紀錄，就立刻鎖定，其他人必須等待直到解鎖（提交）
- MySQL：`SELECT … FOR UPDATE` 鎖住查詢回傳的每一行
- 圖 7.12：T2 必須等 T1 完成；T1 完成後 total_reserved = 100，T2 已無房 → 撤銷交易
- 優點：防止修改正在改或已改過的資料；實作容易，序列化更新避免衝突；資料爭用嚴重時很有用
- 缺點：多資源鎖定可能**死鎖**；**沒有擴展性**，交易鎖太久會讓其他交易無法存取，影響效能
- 結論：**不推薦**在預訂系統使用
- 補充：多日期預訂時以固定順序（ORDER BY date）鎖定，可降低死鎖機率


### 選項 2：樂觀鎖定（版本號）（27:47）

第二種，樂觀鎖。它的心態剛好相反：「應該沒人跟我搶吧」，所以不先上鎖，大家都可以同時嘗試。常見做法有兩種，版本號和時間戳。一般比較推薦版本號，因為伺服器的時鐘可能不準。

做法是四步：一，表裡加一個 version 欄位。二，改資料前，先讀出目前的版本號。三，更新時把版本號加一。四，資料庫確認新版本剛好比舊的多一，不對就代表有人搶先改過，這次作廢，回到第二步重來。

先看順利的情況：使用者一讀到第一版、寫入第二版；之後使用者二讀到第二版、寫入第三版。版本一路往前，大家都成功。

再看衝突的情況：兩個人都讀到第一版。使用者一先寫入第二版，成功。使用者二也想寫第二版，可是資料庫現在已經是第二版了，對不上，交易被中止。

樂觀鎖通常比悲觀鎖快，因為完全不鎖資料庫。但搶的人一多就慘了：大家讀到同一個版本，只有一個人成功，其他人全部重來；下一輪又只有一個成功……結果雖然一定正確，但使用者會一直轉圈圈。八個人要全部訂到，總共得試三十六次。

整理一下。優點：不會改到過時的資料，不用鎖資料庫，衝突少的時候又快又順。缺點：搶的人一多，效能就很差。不過訂房系統每秒才幾筆，所以樂觀鎖是很不錯的選擇。


**重點筆記**

- 又稱樂觀並行控制：允許多個使用者同時嘗試更新同一資源
- 兩種實作：**版本號**、時間戳；版本號較好，因為伺服器時鐘可能不準
- 步驟：① 加 `version` 欄位 ② 修改前先讀版本號 ③ 更新時版本號 +1 寫回 ④ 資料庫檢查新版本應比目前多 1，否則中止並回到步驟 2 重試
- 通常比悲觀鎖快（不鎖資料庫）；但**並行數高時效能急劇下降**：所有客戶端讀到相同版本，只有一個成功，其餘重試…
- 優點：防止編輯過時資料；不鎖資料庫資源，版本邏輯由應用程式處理；爭用少時表現好
- 缺點：資料爭用嚴重時效能很差
- 結論：預訂 QPS 通常不高 → **樂觀鎖是不錯的選擇**
```
UPDATE room_type_inventory
   SET total_reserved = total_reserved + 1,
       version = version + 1
 WHERE hotel_id=? AND room_type_id=? AND date=?
   AND version = ?;   -- 讀到的版本
-- affected rows = 0 → 衝突，重試
```


### 選項 3：資料庫約束（CHECK）（29:50）

第三種，資料庫約束，概念跟樂觀鎖很像。我們直接在庫存表上加一條規則：總數減掉已訂，永遠不能小於零。

用同一個例子：兩個人都看到剩一間。使用者一先訂、先提交，已訂變成 100。

輪到使用者二訂房時，已訂會變成 101，違反了「100 減 101 不能小於零」的規則，整個交易被資料庫退回去。

優點：非常好實作，衝突少的時候效果很好。缺點有三個：搶的人多時，會有一堆人明明看到有房、按下去卻說沒了，很挫折；規則寫在資料庫裡，不像程式碼那麼好做版本控管；而且不是每種資料庫都支援，換資料庫時可能會踩雷。

因為好實作、訂房又不常激烈搶房，這也是很好的選擇。工程上要注意兩件事：MySQL 8.0.16 以前會看得懂 CHECK、但完全不執行；如果要支援 10% 超賣，規則要改成已訂不能超過總數的一點一倍。


**重點筆記**

- 與樂觀鎖非常類似：`CONSTRAINT `check_room_count` CHECK((`total_inventory - total_reserved` >= 0))`
- 圖 7.14：使用者 2 預訂時 total_reserved 變成 101，違反 100 − 101 ≥ 0 → 交易滾回
- 優點：實作容易；資料爭用少時效果不錯
- 缺點：爭用嚴重時大量失敗（看到有房，按下去卻說沒房，使用者沮喪）；約束不像程式碼容易做版本控制；並非所有資料庫都支援，遷移資料庫時可能有麻煩
- 結論：容易實作，且飯店預訂爭用不常見（QPS 低）→ 另一個不錯的選擇
- 補充：MySQL 8.0.16 之前會解析但**忽略** CHECK；10% 超賣需寫成 `total_reserved <= total_inventory * 1.1`


### 實驗室：一步一步重現競爭與鎖（31:13）

🧪 【互動實驗】進實驗室囉。實驗 A 讓你當導演，自己決定兩個交易誰先走哪一步。切換無保護、悲觀鎖、樂觀鎖、資料庫約束四種模式，看每個交易看到什麼數字，最後到底賣出幾間。

🧪 【互動實驗】實驗 B 把規模放大。設定多少人搶、剩幾間房、大家在多短的時間內湧進來，按下模擬，比較四種策略的超賣、失敗、重試，以及最慢的那批人要等多久。也可以按一鍵比較，四種一起跑。


**重點筆記**

- 實驗 A：手動交錯執行 T1／T2 的每個步驟，比較「無保護／悲觀鎖／樂觀鎖／資料庫約束」
- 實驗 B：N 位使用者在 W 毫秒內搶 K 間房，統計超賣、失敗、重試與延遲（離散事件模擬）


### 三種方案比較與選擇（31:54）

我們把三種方案並排比較一下。

結論：訂房系統每秒交易量不高，樂觀鎖或資料庫約束都很適合，悲觀鎖不推薦。真正的系統通常會多層防守：API 層用冪等鍵擋重送，資料層用樂觀鎖或約束擋超賣，狀態機再擋非法的狀態轉換。


**重點筆記**

方案建議悲觀鎖不推薦（死鎖、擴展性）樂觀鎖推薦（QPS 低、爭用少）資料庫約束推薦（容易實作）實務上常疊加：API 層冪等鍵防重送 + 資料層樂觀鎖／約束防超賣。


## 第 7 章　第 3 步・深入③：系統的擴展


### 當流量放大 1,000 倍（32:20）

平常訂房系統的流量不大。但面試官很可能追問：如果不只是自家官網，還要接 Booking.com、Expedia 這些大平台呢？流量可能直接放大一千倍。

流量大了，先找瓶頸在哪。我們的服務都是無狀態的，加機器就能撐。但所有狀態都在資料庫裡，而資料庫可沒辦法說加幾台就加幾台。


**重點筆記**

- 追問：若不只服務連鎖飯店官網，還要支援 booking.com、expedia.com 等熱門旅遊網站 → QPS 可能高出 **1,000 倍**以上
- 所有服務都是**無狀態（stateless）**，加伺服器即可擴展
- 所有狀態都在資料庫，而資料庫無法靠「簡單多加幾台」擴展 → 瓶頸


### 資料庫分片（Sharding）（32:51）

第一招是分片：把資料拆到好幾台資料庫，每台只顧一部分。前面看過，大部分查詢都會帶 hotel_id，所以就用它來切。

圖上把資料分成十六片。預訂服務收到請求，就用 hotel_id 除以十六取餘數，決定要去哪一片找資料。

假設每秒三萬次查詢，分成十六片之後，每片大約一千八百七十五次，一台 MySQL 就扛得住。

工程師補充：取餘數有個代價。從十六片變十七片時，大部分資料都得搬家。實務上常用一致性雜湊，或者一開始就切很多邏輯分片，再對應到實體機器。另外，超熱門的飯店可能讓某一片特別忙，要另外盯著。

🧪 【互動實驗】換你試試。輸入飯店 ID 看它被分到哪一片；調整分片數，看每片負擔多少；最後比較一下取餘數和一致性雜湊，加一片時各要搬多少資料。


**重點筆記**

- 把資料拆分到多個資料庫，每個只負責保存一小部分
- 大多數查詢都用 hotel_id 篩選 → 按 hotel_id 分片
- 圖 7.15：16 個分片，路由 `hotel_id % 16`
- QPS 30,000 → 每片 30,000 ÷ 16 = **1,875 QPS**，在單台 MySQL 負荷範圍內
- 補充：取餘數在增減分片時大量搬遷資料，可用一致性雜湊或預切邏輯分片；注意熱門飯店造成的熱點分片


### 快取：Redis 庫存快取（圖 7.16）（34:07）

第二招是快取。庫存資料有個特性：只有今天以後的資料有意義，因為沒人會訂昨天的房。所以我們希望資料能自動過期，真要查歷史，再去別的地方找。

這剛好是 Redis 的強項。它可以設定存活時間，時間到就自動刪除；記憶體滿了，還會把最久沒人用的資料先踢掉。

如果要做到 Booking.com 的規模，就在資料庫前面加一層快取。查庫存走快取，更新庫存寫資料庫，資料庫再非同步地把變動同步給快取。大部分的請求，在快取這一層就處理掉了。

仔細看一下元件。預訂服務提供三支庫存 API：查一段日期某房型還剩幾間、訂房時已訂加一、取消時把庫存改回來。快取是一個鍵值對：鍵是飯店、房型加日期，值就是那天還剩幾間。

查庫存的次數，比訂房多上一個數量級，大部分都由快取回答。但記住：就算 Redis 說還有房，下單時還是要回資料庫再確認一次。資料庫，才是庫存唯一可信的來源。


**重點筆記**

- 只有目前與未來的庫存有意義 → 需要 **TTL**，舊資料自動過期；歷史資料到別的資料庫查
- Redis：TTL + LRU（Least Recently Used）快取收回策略
- 預訂服務：查詢庫存走快取；更新庫存寫資料庫；資料庫以非同步方式更新快取
- 庫存快取（Redis）：鍵 `hotelID_roomTypeID_{date}` → 值：可預訂房間數
- 讀取（查庫存）遠多於寫入，大多由快取回應
- **庫存資料庫才是事實來源（source of truth）**：Redis 顯示有房，仍要在資料庫再檢查一次
- 預訂服務的庫存 API：查詢日期範圍內可訂數量；預訂時 total_reserved + 1；取消時更新庫存


### 快取帶來的新挑戰：一致性（35:37）

加了快取，擴展性和吞吐量都上來了，但也帶來一個新麻煩：資料庫和快取的資料，怎麼保持一致？我們看客人訂房時，系統會做哪兩件事。

第一，查庫存：透過快取看還有沒有房。第二，更新庫存：先寫資料庫，再非同步把變動同步到快取。

同步的方式有兩種。一是在程式裡，寫完資料庫順手更新快取。另一種是變動資料擷取，簡稱 CDC：用 Debezium 這類工具監聽資料庫的變動紀錄，再自動套用到 Redis。

因為是先寫資料庫、後同步快取，中間一定有個時間差。可能資料庫已經沒房了，快取卻還寫著剩一間。

其實這沒想像中嚴重，只要下單時有回資料庫驗證就好。客人看到剩一間，按下訂房，資料庫一查發現沒了，就回一句「不好意思，最後一間剛被訂走」。等他重新整理，快取早就同步好了，也就不會再看到空房。

快取的優點：資料庫輕鬆很多，因為讀取都被快取接走了；速度也快，資料直接從記憶體拿。缺點：資料庫和快取的一致性真的不好維護，你得仔細想想，這種不一致對使用者體驗有什麼影響。

🧪 【互動實驗】換你試試。調整同步延遲和搶房人數，按下開始，看快取和資料庫的數字怎麼追趕。你會發現延遲越長，「看得到卻訂不到」的人越多；但只要下單時回資料庫驗證，超賣永遠是零。也可以關掉驗證，看看錯誤示範有多慘。


**重點筆記**

- 新挑戰：資料庫和快取之間如何保持一致
- 訂房時兩個操作：① 查詢庫存（透過快取）② 更新庫存：先更新資料庫，再非同步傳播到快取
- 非同步傳播：應用程式碼呼叫，或 **CDC（change data capture）**：如 **Debezium** 來源連接器讀取資料庫變動 → 套用到 Redis（Redis sink）
- 快取可能沒有即時反映最新庫存：資料庫已無房，快取仍顯示有房 → 使用者嘗試預訂 → 資料庫驗證失敗 → 回錯誤；重新整理後快取已同步
- 優點：降低資料庫負載；高性能（記憶體）。缺點：維持一致性困難，要思考對使用者體驗的影響


## 第 8 章　第 3 步・深入④：微服務的資料一致性


### 混合式設計 vs 純粹微服務（圖 7.17）（37:46）

傳統的單體架構，大家共用一個資料庫，一致性很好處理。我們的設計其實是混合式：預訂服務同時負責訂單和庫存，所以兩張表放在同一個資料庫裡，前面講的那些鎖和 ACID，才能直接派上用場。

不過，如果面試官是微服務的基本教義派，他可能會挑戰你：每個服務都應該有自己的資料庫才對。就像右邊這樣，三個服務、三個資料庫。


**重點筆記**

- 傳統單體架構：共用一個關聯式資料庫確保一致性
- 本設計採**混合式**：預訂服務同時處理預訂與庫存 API，庫存表與預訂表在**同一個**關聯式資料庫 → 可直接用 ACID 處理並行問題
- 純粹微服務主義者：每個微服務都要有自己的資料庫（圖 7.17 右）


### 不一致是怎麼發生的（圖 7.18／7.19）（38:25）

我們用兩個服務來說明就好，真實世界可能有好幾百個。如果是單體架構，扣庫存和建訂單可以包在同一個交易裡，要嘛一起成功、要嘛一起失敗。

但拆成微服務後，每個服務都有自己的資料庫。原本應該一次完成的動作，現在跨了兩個服務，變成兩個獨立的交易，沒辦法用一個交易保證一致了。

萬一訂單寫入失敗，你就得記得回頭把庫存加回去。做對的方法只有一種，出錯的方式卻有一百種：服務掛掉、逾時、重試導致重複扣、補償本身又失敗、訊息遺失……每一種都可能讓資料對不起來。


**重點筆記**

- 單體架構：「管理房間庫存」與「預訂房間」包在**單一交易**，維持 ACID
- 微服務架構：每個服務有自己的資料庫，邏輯上應具原子性的操作跨越多個服務 → 無法用單一交易保證一致
- 若預訂資料庫更新失敗，必須記得把庫存資料庫的已訂數量恢復
- 「把事情做對的方式只有一種，但出問題的情況卻有百百種」


### 兩階段提交（2PC）（39:21）

業界有幾個經過驗證的解法。第一個是兩階段提交，簡稱 2PC。它是一種資料庫協定，保證跨好幾個節點的交易，要嘛全部成功，要嘛全部失敗。

第一階段叫準備：協調者問每個參與者「你可以提交嗎？」參與者先把事情做好、資源鎖住，然後投票說可以或不行。

第二階段叫提交：大家都說可以，協調者才喊「提交」；只要有一個說不行，就通知所有人回滾。

問題是，2PC 會卡住。只要有一個節點掛掉，比如協調者在準備完之後當機，參與者就只能拿著鎖乾等，不能自己提交也不能自己回滾，直到協調者恢復。所以它的效能並不好。


**重點筆記**

- 2PC（Two-phase commit）：資料庫協定，保證跨多節點交易提交的**原子性**：要嘛所有節點都成功，要嘛全部失敗
- 階段 1 Prepare：協調者詢問各參與者是否可提交（參與者鎖住資源並投票）
- 階段 2 Commit／Abort：全票同意才提交，否則全部回滾
- **阻塞型（blocking）**協定：單一節點故障，整體進度被阻塞直到恢復 → 效能不高


### Saga 與補償交易（40:23）

第二個解法是 Saga。它把一件大事拆成一連串的小交易，每個服務做完自己的本地交易，就發一個訊息，觸發下一個服務接手。

如果中間某一步失敗，Saga 就倒著執行補償交易，把前面做過的事一件一件撤銷。例如付款失敗：訂單改成已拒絕，庫存的已訂數量減回去。

兩者的差別：2PC 是一次提交、強一致；Saga 是很多小步驟，依賴最終一致性。所以 Saga 的過程中，會有短暫的不一致，例如庫存已經扣了，但訂單還沒建立。

🧪 【互動實驗】換你試試。選 2PC 或 Saga，再選一個故障點，按下執行。看每個服務的狀態怎麼變、有沒有資源被鎖住、中間有沒有不一致，最後資料又是怎麼回到一致的。


**重點筆記**

- Saga：一系列的**本地交易**；每個交易更新後發佈訊息，觸發下一個步驟
- 某步驟失敗 → 執行一連串**補償交易（compensating transaction）**撤銷先前的變動
- 2PC：單一次提交執行 ACID 交易；Saga：多步驟組成，依賴**終究一致性（eventual consistency）**


### 架構師的取捨（41:29）

要注意的是：要解決微服務之間的不一致，一定得用上這些複雜的機制，整體設計會複雜很多。身為架構師，你要先問自己，這些複雜度值不值得。

以這題來說，書上的判斷是不值得，所以用更務實的做法：把訂單和庫存放在同一個關聯式資料庫。這不是偷懶，而是有意識的取捨：不需要拆的，就別硬拆。


**重點筆記**

- 解決微服務資料不一致，一定會用到複雜機制，大大增加整體設計的複雜度
- 架構師要先判斷：增加的複雜度值不值得
- 本題結論：**不值得** → 採用更實用的做法：把預訂和庫存資料都保存在同一個關聯式資料庫中


## 第 9 章　第 4 步：匯整總結與延伸


### 系統驗證：防禦雙重預訂的完整生命週期（42:04）

最後，我們把所有防線串起來走一次。使用者在尖峰時刻連點了兩次，兩個帶著同一個 reservationID 的請求，同時衝進 API 閘道器。

閘道器做完限流和身分驗證，把請求交給預訂服務。預訂服務靠冪等鍵認出第二個是重複的，直接回傳第一筆的結果。

第一個請求進到資料庫，在一個 ACID 交易裡，用樂觀鎖或資料庫約束扣掉房型庫存，保證不會超賣。

交易成功、付款完成，狀態機往前推，訂單從待處理變成已付款。

這就是今天最重要的心得：好的架構從來不是靠某一招，而是 API 層、應用層、資料層，每一層各守一道關。


**重點筆記**

- 高併發請求到達（兩次點擊、相同 reservationID）
- 冪等性攔截：預訂服務識別並忽略第二個重複請求
- ACID 鎖定：運用關聯式交易安全，扣減房型庫存，避免超賣
- 狀態推進：狀態機由 Pending 轉為 Paid**Takeaway：完美的架構並非仰賴單一技術，而是 API 層、應用層與資料層的協同防禦。**


### 章節摘要（心智圖）（43:04）

我們回顧一下。第一步，問清楚功能和非功能需求，再做粗估，知道規模有多大。第二步，設計 API、第一版資料模型，還有整體架構圖。

第三步深入設計：發現客人訂的是房型不是房間，所以改成 roomTypeID 和庫存表；接著處理搶房問題，比較悲觀鎖、樂觀鎖和資料庫約束；然後用分片和 Redis 快取來擴展；最後討論微服務的一致性，認識 2PC 和 Saga。第四步就是收尾總結。


**重點筆記**

- 第 1 步：功能性需求（預訂房間、管理面板、超額預訂）、非功能性需求（高並行、中等延遲）
- 第 2 步：API 設計（飯店、房間、預訂）、資料模型（查看飯店、找可訂房、進行預訂、查預訂紀錄）、高階設計
- 第 3 步：改進資料模型（roomTypeID）、並行問題（悲觀鎖、樂觀鎖、資料庫約束）、可擴展性（分片、快取）、服務間資料一致性
- 第 4 步：匯整總結


### 延伸思考：秒殺級的航空訂位怎麼辦？（43:46）

最後來兩個面試常見的延伸題，這兩題來自課程影片的討論，不在原書範圍裡。第一題：如果把這套架構搬去做航空公司的秒殺搶票，流量高好幾個數量級，要怎麼改？

常見的做法是把扣庫存這件事往前移到 Redis，用原子操作或 Lua 腳本先預扣。扣到的人進到訊息佇列，再慢慢寫回資料庫；沒扣到的人在記憶體這一層就被擋掉，根本不會碰到資料庫。

代價是 Redis 和資料庫之間變成最終一致，需要對帳和補償，例如預扣成功但付款失敗，就要把庫存加回去；Redis 的持久化和故障切換也得設計好。不過回到我們的題目，飯店每秒才 3 筆交易，完全不需要這麼複雜。架構要跟著規模走。

第二題：Saga 和我們的混合式設計怎麼選？如果流程跨到外部系統，例如金流商，根本沒辦法放進同一個資料庫交易，那 Saga 加補償幾乎是唯一解。但像庫存和訂單這種綁得很緊、又是同一個團隊管的資料，放在同一個資料庫用 ACID，最簡單也最可靠。


**重點筆記**

（本節延伸自影片教材中的提問，不在原書第 7 章範圍內）
- 問題：若併發高出好幾個數量級（例如航空公司秒殺），資料庫逐筆鎖定或樂觀重試都會撐不住
- 思路：把庫存扣減前移到 Redis，用原子操作（`DECR`／Lua 腳本）預扣；成功者進入佇列，非同步寫回資料庫；失敗者在記憶體層就被擋下
- 代價：Redis 與資料庫之間變成終究一致，需要對帳與補償（預扣成功但付款失敗要加回庫存）、Redis 持久化與故障切換也要設計
- 回到本章：飯店系統 TPS≈3，不需要這麼複雜 → 架構要跟著規模走
