# YouTube 持續模擬世界

目前第 14 章保留兩個入口：預設及 `mode=lesson` 開啟 **12 個月策略課程原本的完整架構圖**；`mode=world` 開啟 **即時流量與故障**。兩個入口共用同一個 deterministic World；切換時序列化並接手完整快照，而非依畫面數字重建。共用內容包含月份、模擬時鐘與 RNG、觀眾身份與弱網分群、地區、實體機器、故障、影片、Request、重試與完成進度。課程專用評分及版面偏好仍留在課程存檔。

新增人數可選 1／5／10／100。選取群組及移動人數，再按「移入弱網」或拖到訊號不良區，即依觀眾身份拆分；同批觀眾移回正常時合併。受影響群組有斜線覆蓋，已送出的示意片段保留並即時按 0.4 Mbps 推進，正常群組為 12 Mbps（每個示意片段 40 Mbit）。圖中的新增觀眾數與課程月份的尖峰需求估計分別標示，不混充同一數字。新增與拆分只更新節點，不重建 SVG、不清除上傳與 LOG。

## 套用架構設計

架構設計模式的八項決策會直接決定這個世界怎麼跑，contract 定義在 `youtube-world.js` 的 `DESIGN_EFFECTS`（兩套引擎共用同一組 optionId，有測試在守）：

| 決策 | 在世界裡的效果 |
| --- | --- |
| `cdnTier` | `off` 關閉邊緣快取，每次觀看都回源；`all` 全部快取；`popularOnly` 只快取觀看數前三名的影片，長尾一律回源 |
| `streamRedundancy` / `apiRedundancy` | `off` 每區 1 台且故障不自動恢復；`autoScale` 每區 1 台、同區持續滿載 180 秒補 1 台；`warmStandby` 每區開場就 3 台 |
| `dbMasterSlave` | `off` DB 故障不自動恢復；`manual` 300 秒；`auto` 30 秒 |
| `cacheReplica` | Metadata 快取節點數 1／2／3；快取節點全掛時 metadata 讀取才會壓回 Metadata DB |
| `transcodeResilience` | `off` 轉碼任務失敗就卡住；`reassign` 換機器但從頭重轉；`checkpointResume` 換機器並保留已完成進度 |
| `preSignedUpload` / `resumableUpload` | 對應 `options.directUpload` 與 `options.resumable` |

沒有任何架構設定時（例如從沒進過課程模式），世界用 `DESIGN_DEFAULTS` 跑，行為與加入這個功能前相同。世界頂端的「套用中的架構」會列出八項各自的效果並標示哪幾項與預設不同；改完決策要按「同種子重新開始」才會套用，或按「改用預設架構」清除。

架構圖與觀眾圖共用人數、buffer、機器、CDN 選項、Request、隨機數狀態與模擬時間。只有 12 月策略課程的月份／評分獨立保存；課程架構決策仍依原契約作為重置世界時的初始配置。

## 操作

- 全場預設只有「觀眾 #1（我）」1 人，新增人數可選 1～10 人，初始選擇為 1 人。既有觀眾持續觀看、搜尋、上傳與離開，持續人流只替換離開的觀眾，不會自行擴增總人數。可逐次加到 500 人；這是操作上限，不是預設機器的容量保證。超過 100 時畫布抽樣顯示，指標計算全部 session，所有人的模擬仍逐 tick 執行。
- 點觀眾或用選單追蹤同一 session。拖曳觀眾跨區／進入右下弱網區，或用側欄調整位置、路由、五級網路。離線會先耗盡緩衝再等待；CDN 不能繞過最後一哩瓶頸。
- 點機器只選取。側欄提供關閉、恢復與同區加機。已在傳輸的請求會逾時，退避後選擇健康機器；CDN 不可用時回源。
- 單一 0.1 秒模擬時鐘控制所有工作。1x 等同真實時間，另有 5x／20x、暫停與單步。每幀最多 4 個 tick（0.4 模擬秒），運算達 6ms 後不再開始下一個 tick；單一 tick 不可中斷，因此 6ms 是軟預算。慢幀的待跑時間完整保留，不夾限、不跳步。工具列顯示目標倍率、近 1 秒實際倍率與待跑模擬秒數；電腦負荷過高時可主動改選 1x／5x，讓待跑時間逐步消化。暫停、切速、分頁隱藏與模式切換都保留既有待跑量；隱藏期間不新增待跑量。單步推進 0.1 秒並抵掉相應待跑量，只有明確重置世界才清空。
- 上傳使用教材 multipart 模型：建立 Metadata/session，客戶端 6 塊、最多 2 塊並行，原檔確認完整後檢查格式，再平行轉 360p／480p／720p 與縮圖，最後發布。每個階段使用同一 video ID。重試保留已確認塊／已完成任務，可關閉續傳作比較。
- 點 Request ID 可看機器路徑與每次重試。列表最新在前，可分頁與依使用者／機器／失敗篩選。聚焦列表按鈕時保留列表位置，離開焦點後繼續刷新；詳細 trace 仍更新。
- 自動故障首發在第 45 模擬秒，此後間隔 45–90 秒；預設 25 秒後修復。兩者均可關閉，手動故障仍可操作。事故紀錄包括受影響使用者、失敗嘗試、恢復與耗時。

## 檔案與驗證

- `youtube-world.js`：無 DOM、固定步長、可播種的共同狀態模型；`DESIGN_EFFECTS` 是與課程模式的唯一契約。
- `youtube-modes.js`：兩個模式的入口、各自的進度保存，以及共用的架構決策（`youtube-architecture-v1`）。
- `youtube-world-ui.js`：選取、拖曳、播放器、請求路徑、資料檢視。
- `youtube-world.css`：桌面／窄視窗版面；重要控制至少 44px，地圖角色另有選單等效操作。
- `tests/youtube-world.test.cjs`：使用 Node 內建測試工具，執行 `node --test software-learning/tests/youtube-world.test.cjs`。

既有 20 個自動驗證涵蓋：100 個 session、斷網續播、弱網與 CDN、機器故障切換、續傳與不續傳、轉碼重派、新增據點不搬人口、播放時走動、持續人流、種子確定性、最新 Request 保留、CDN 故障回源；以及架構決策聯動的 7 項：兩套引擎詞彙一致、壞設定退回預設、熱備援機器數、DB 恢復時間、快取複本與 DB 回壓、轉碼容錯三種行為、熱門影片快取政策。

瀏覽器實測涵蓋桌面與窄視窗、弱網等待、背景持續運行、自動故障／恢復、按鈕關機／恢復、加機、加人、建立據點。正式部署尚未執行。

## 教學假設與邊界

這是瀏覽器內的教學模型，不傳送真實影音；Mbps、容量、任務工作量及故障時間是可比較的示例假設。上傳示範採 multipart，並非 YouTube Data API 的實際 sequential resumable upload 協定。初始化影片的前 5 秒視為已預載。

CDN 依地區、影片、畫質及片段記錄快取，沒有容量淘汰／TTL；流量有 bytes 與跨區計數，尚未套用真實價格。轉碼以工作量與相依任務模擬，失敗從該任務重做，沒有執行實際編碼或 GOP 切割。Metadata DB 是可用性與容量模型，沒有宣稱已模擬 Master 選主、複寫延遲、Quorum 或 DRM。原課程的進階策略仍保留在課程模式，沒有用無作用的開關加入新世界。

世界的設定與狀態目前在記憶體內，重新載入會重建。種子重設重播的是相同初始世界與隨機序列；若手動干預不同，結果也會不同。

## 容量觀察與瓶頸轉移

指標列下方會指出「目前瓶頸」，並標示相關機器卡片。判定依最近一個 tick 的同類、同區共用佇列等待數排序，以工作槽占用率破同分；同一 pool 的每台機器記錄的是同一批等待請求，因此取最大值而非加總。故障且沒有健康機器時也會顯示等待原因與 0 個健康工作槽。這是瞬時排隊觀察，不是所有延遲原因的定論；沒有容量排隊也可能有重試、傳輸、跨區或最後一哩問題，仍要追蹤觀眾與 Request。

按「查看瓶頸機器」會選取對應機器並帶到操作面板，再按「同區加一台」擴充。共用後端的物件儲存、Metadata DB、轉碼 Worker 與 Metadata 快取均沿用相同操作，每種每區最多 8 台。提示同時顯示其他排隊據點，避免只看到單一最高數字。加人提示會引導查看容量，並提醒只加前端可能把壓力推向共用後端。

可重現基準：`new World(14, n)`，僅關閉 `autoFaults`，其他維持預設，執行 1200 次 `step(.1)`。失敗率為 `failed / (completed + failed)`（失敗嘗試，包含重試）。修改前後容量完全相同：

| 人數 | 再緩衝 | 失敗嘗試率 | 佇列 |
| --- | --- | --- | --- |
| 50 | 24.2% | 0.0% | 13 |
| 100 | 47.4% | 10.6% | 54 |
| 300 | 68.2% | 39.7% | 257 |
| 500 | 75.9% | 51.9% | 466 |

300 人、120 模擬秒時，物件儲存有 118 筆等待、16/16 工作槽；美國 CDN 有 53 筆等待。每區的串流／API／CDN 各加 3 台，再緩衝為 27.9%、失敗 5.7%；各加 7 台反升為 41.5%、17.5%；各加 7 台且物件儲存加 3 台，才降到 1.2%、0.0%（未四捨五入失敗率為 0.0395%）。此時最高等待轉為 Worker 5 筆。容量、重試、緩衝與瓶頸轉移都沒有為了畫面效能而簡化。

新增 8 個模型／推進測試涵蓋慢幀上限、時間預算、完整積欠重播與切速、單步、物件儲存判定、共用佇列去重、瓶頸轉移、後端故障。執行 `cd software-learning && node --test tests/youtube-world.test.cjs tests/check-interactive-blocks.js`：28 項世界測試（既有 20 + 新增 8）與 2 項互動內容檢查全部通過。

### 重現部分 API 請求逾時

1. 在「實際運作」按「API 壓力測試」（架構設計工具列也有入口）。
2. 暫停世界，為了隔離變因可在進階控制關閉隨機故障與持續進出。
3. 使用只有一台健康 API 的區域，設定並行上限 2、總吞吐 2 Mbps、等待逾時 2 秒，按「套用到這台 API」。
4. 同時送出 10 筆查詢，每筆回應模擬 0.5 MB；單步後可看到 2 筆處理、8 筆排隊。既有請求也共用容量，所以有背景工作時數字可能不同。
5. 繼續世界或單步超過 2 秒，排隊請求會記錄容量滿與逾時，再退避重試。點 Request ID 在右側看完整嘗試原因。
6. 調高容量（例如 16 筆、32 Mbps、12 秒）或同區加機，觀察原批次恢復。失敗嘗試不等於最終失敗；原有重試上限仍適用。

壓測使用獨立客戶端，與現有請求共用真實模擬工作槽，不會替換觀眾 session。同區多台 API 使用最短設定等待期限；無健康 API 仍走原有 12 秒等待及故障重試。此實驗位於 World 模型，架構設計的背景負載估值並未改成此模型。固定步長、補跑與六項架構契約保持不變。
